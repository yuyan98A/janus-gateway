# 全能多云反向代理网关架构设计方案
## 统一多云算力（Google Antigravity & OpenAI Codex）⇋ 全场景 Agent 客户端

---

## 1. 系统愿景与核心定位

### 1.1 核心定位：虚拟模型提供商（Virtual Model Provider）
本项目的终极目标是打造一个**本地/私有化的“虚拟模型提供商”网关**。
* **对下游客户端（Downstream Consumers）**：
  网关彻底屏蔽底层算力异构性，不对任何具体客户端做私有绑定。网关对外统一暴露全球通用两大标准接口：
  1. **Anthropic Messages 接口规范**：`POST /v1/messages`、`GET /v1/models`；
  2. **OpenAI Chat Completions 接口规范**：`POST /v1/chat/completions`、`GET /v1/models`。
  下游无论是 **Claude Code CLI**、**Cursor**、**Cline**、**Roo Code**、**Aider** 还是任何自研 Agent，都只需将 `baseURL` 指向本地网关并填入自定义统一密钥，即可透明调度多云全量前沿模型。

* **对上游云端算力（Upstream Compute）**：
  聚合两大主力原生订阅与环境算力，实施高可用的统一编排：
  1. **Google Antigravity 专线**：复用本地 `acc`，调用 Google Cloud Code PA 内部接口，无缝消耗 Google One / Antigravity 赋予的配额（提供 Claude Sonnet 4.6、Opus 4.6 以及 Gemini 3.8/2.5 系列）；
  2. **Codex 算力专线**：参考 `ccr` 核心能力，自动导入本机 Codex CLI / ChatGPT 订阅登录态，调用 Codex 专属后端（`chatgpt.com/backend-api/codex/responses`），使用该登录态可用的 Codex 模型（如 `gpt-6.1-sol`、`gpt-6-astra`、`gpt-5.5`、`gpt-5.6-sol`）。

  网关不连接 `api.openai.com/v1` 商业 API，也不接受商业 API Key 配置。OpenAI Chat Completions 仅作为下游兼容协议入口，模型请求由 Google 或 Codex 上游处理。

## 4. Codex 算力专属驱动深度设计

### 4.1 本地登录态捕获与 OAuth 2.0 自动换票机（Auth Engine）
Codex 算力的本质是**复用用户已在本机登录的 ChatGPT / Codex 订阅环境**，实现与商业 API 无关的高并发免费算力调用。

1. **本地凭据发现**：
   * 网关启动时自动读取 `~/.codex/auth.json`（Windows 位于 `%USERPROFILE%\.codex\auth.json`）；
   * 从文件解析 `tokens`:
     * `access_token`：当前用于调用的 Bearer 令牌；
     * `refresh_token`：用于定期续期的 Refresh 令牌；
     * `account_id`：ChatGPT 组织/账户 ID；
     * `id_token`：包含用户声明的 JWT。
2. **JWT 声明提取**：
   * 解码 JWT payload，从 `https://api.openai.com/auth` 命名空间中提取 `chatgpt_account_id` 与 `chatgpt_account_is_fedramp`。
3. **静默自动换票机**：
   * 当 Token 即将过期（距离 `exp` 小于 60s）或上游返回 `401 Unauthorized` 时，自动发起换票请求：
     ```http
     POST https://auth.openai.com/oauth/token
     Content-Type: application/json

     {
       "client_id": "app_EMoamEEZ73f0CkXaXp7hrann",
       "grant_type": "refresh_token",
       "refresh_token": "<refresh_token>",
       "scope": "openid profile email offline_access api.connectors.read api.connectors.invoke"
     }
     ```
   * 采用 Single-Flight 并发锁机制，确保多并发请求只触发一次换票；
   * 换票成功后立即静默回写更新 `~/.codex/auth.json`，确保本机 Codex CLI 与网关双向同步。
4. **上游请求头封装**：
   * `Authorization: Bearer <access_token>`
   * `ChatGPT-Account-ID: <account_id>`
   * `User-Agent: codex-cli`
   * `Accept: text/event-stream`

### 4.2 协议转换引擎（Request Adapter: Downstream ⇋ Responses API）
Codex 专线后端跑的是 OpenAI **Responses API 规范**（`POST https://chatgpt.com/backend-api/codex/responses`），而非传统 Chat Completions。适配器需完成双向转换：

#### 1. Anthropic Messages ➔ Codex Responses API
* **System Prompt 映射**：提取 `system` 字段，作为 Responses 的顶层 `instructions`（默认兜底 `You are a helpful assistant.`）；
* **Message 对话历史映射**：
  * 普通文本 ➔ `input: [{ type: "message", role, content: [{ type: "input_text", text }] }]`
  * 图片内容 ➔ `content: [{ type: "input_image", image_url }]`
  * 工具使用历史（`tool_use`）➔ `type: "function_call", id, call_id, name, arguments`
  * 工具结果回填（`tool_result`）➔ `type: "function_call_output", call_id, output`
* **工具定义转换**：
  * Anthropic `tools: [{ name, description, input_schema }]` ➔ Responses `tools: [{ type: "function", name, description, parameters }]`
* **Codex 上游硬性约束注入**：
  * 强制注入 `"store": false`（防止云端落库报错）；
  * 强制注入 `"stream": true`。

#### 2. OpenAI Chat Completions ➔ Codex Responses API
* `messages` 中的 `system`/`developer` 提取为 `instructions`；
* `assistant` 中的 `tool_calls` 展开为 `function_call` 条目；
* `role: "tool"` 映射为 `function_call_output`。

---

### 4.3 流式 SSE 状态机适配器（Stream Adapter）
Codex 后端流式返回标准的 Responses SSE 数据包，网关将其实时解码并组装为下游所需的 SSE 格式：

#### 1. Responses SSE 事件解析表
| 上游 Responses 事件 | 携带数据 | 映射到 Anthropic SSE | 映射到 OpenAI Chat SSE |
| :--- | :--- | :--- | :--- |
| `response.created` / `in_progress` | `response.id`, `model` | 发出 `message_start` | 初始化 chunk ID 与模型 |
| `response.output_item.added` (item=message) | `item.id`, `role` | 发出 `content_block_start` (`type: text`) | 准备生成正文 |
| `response.output_item.added` (item=reasoning) | `item.id` | 发出 `content_block_start` (`type: thinking`) | 准备生成思维链 |
| `response.output_item.added` (item=function_call)| `item.name`, `call_id` | 发出 `content_block_start` (`type: tool_use`) | 发出首个 `tool_calls` 块 |
| `response.output_text.delta` | `delta: string` | 发出 `content_block_delta` (`text_delta`) | 发出 `delta.content` |
| `response.reasoning_text.delta` | `delta: string` | 发出 `content_block_delta` (`thinking_delta`) | 发出 `delta.reasoning_content` |
| `response.function_call_arguments.delta` | `delta: string` (JSON 片段) | 发出 `content_block_delta` (`input_json_delta`) | 发出 `delta.tool_calls.function.arguments` |
| `response.output_item.done` | 块结束 | 发出 `content_block_stop` | 无 |
| `response.completed` | `usage`, `finish_reason` | 发出 `message_delta` + `message_stop` | 发出 `finish_reason: "stop"/"tool_calls"` 与 `usage` |

### 4.4 模型注册、持久化缓存与确定性路由（Model Registry & Deterministic Routing）
1. **Codex 算力专线动态直连（无别名/去归一化）**：
   * 网关直接发起 `GET https://chatgpt.com/backend-api/codex/models?client_version=0.162.1` 动态获取当前账号全部可用模型；
   * 若离线则优雅回退至本地 `~/.codex/models_cache.json`；
   * **不做任何别名映射与归一化**：上游模型 ID 是什么就呈现什么（如 `gpt-6.1-sol`、`gpt-6-astra`、`gpt-reserve`、`codex-auto-review`），彻底废除 `codex`、`gpt-5-codex` 等隐式别名。
2. **Google 专线全量保留与分类挂载（Categorization）**：
   * 上游 `fetchAvailableModels` 返回的所有条目（含内部测试模型、代码补全、生图、语音转录）**全部保留，不进行过滤**；
   * 自动分配多维分类标识：`chat`（通用对话/推理）、`code_completion`（代码补全）、`image`（生图）、`audio`（语音）、`internal`（内部条目）、`command`（指令）。
3. **持久化缓存与手动差量刷新（Persistent Cache & Diff Reporting）**：
   * 缓存保存在 `./data/models-cache.json`，记录 `updatedAt` 与全量模型元数据；
   * **永不自动过期**：没有自动后台轮询；
   * **手动差量比对**：运维通过 Web 页面或 `POST /v1/admin/models/refresh` 触发刷新；网关比对 `added`、`removed`、`modified`，**仅在检测到有条目变动时更新时间戳并写盘**，并向客户端返回详尽的变更汇报。
4. **确定性路由分流调度（Deterministic Routing）**：
   * **彻底废除前缀与关键词启发匹配**（严禁依据 `includes('claude')`、`includes('gpt')` 等猜测）；
   * 分流中枢（`Dispatcher.resolveProvider`）严格按序判定：
     1. 匹配 `config.json` 的 `routes` 显式路由配置；
     2. 精准匹配已发现 Google 模型 ID 集合；
     3. 精准匹配已发现 Codex 模型 ID 集合；
     4. 若均未命中，直接拒绝请求并返回 HTTP 400（`Unknown model. No route configured and not found in discovered models`）。
   * 详见[模型分类与确定性路由改造规范](./模型分类与确定性路由改造_2026-10-16.md)。
5. **Codex 推理强度能力表**：`models-cache.json` 只负责发现模型 ID，不作为推理能力依据。仅将真实探测接受的 `none`、`minimal`、`low`、`medium`、`high`、`xhigh` 档位写入 `providers.codex.reasoning.models`。OpenAI `reasoning_effort` 直接映射，Anthropic `thinking.budget_tokens` 按配置的预算阈值转换为 `low`/`medium`/`high`；未传强度时省略上游 `reasoning`，未登记或未支持的显式强度返回 400，不静默降级。管理页面支持单模型管理和全 Codex 专线模型顺序批量探测保存，失败模型不会中断批次。细节见[Codex 推理强度 API 文档](../api/Codex推理强度API.md)。
6. **Codex 订阅额度**：管理页面可手动读取 Codex 使用窗口，展示上游提供的已用/剩余百分比、重置时间及可选的额度重置次数。此功能读取 Codex 内部只读用量端点，不触发模型推理；字段和端点可能随上游变化。详细说明见[Codex 推理强度与账号状态 API 文档](../api/Codex推理强度API.md)。
7. **全网关思考强度统一规范**：Google 专线与 Codex 专线的双协议入站优先级、Google Level/Budget 双模与输出上限联动、Codex 阈值分档换算、出站流式思考投影与全流程架构总览见[多云思考强度统一转换与协议对齐规范](./多云思考强度统一转换与协议对齐规范.md)。

## 8. Google 多账号池（Google Account Pool）与手动凭据管理

网关内置自包含的 **Google 多账号池 (`GoogleAccountPool`)**，用于管理凭据并固定使用当前合格账号：

### 8.1 架构设计特点
1. **完全自包含凭据存储**：
   * 默认读写项目内部文件 `./data/google-accounts.json`（已加入 `.gitignore` 防止泄露）；
   * 若初始为空，支持平滑导入本地 `~/.config/antigravity-proxy/accounts.json` 进行冷启动引导；
   * 采用原子写入（`*.tmp` + rename）与热重载（外部编辑即时生效）。
2. **固定账号优先选择**：
   * 请求持续使用当前启用、凭据有效且满足模型推理能力证据约束的账号。当前账号被停用、标记失效或不满足能力证据时，在发起请求前选择其他合格账号。
   * 每次推理选定一个账号和一个 PA 端点。网络异常、408、429、5xx 在同一账号和端点最多尝试 3 次，间隔 250/500 毫秒；其他 4xx 不重试。响应流开始后不重试；不触发冷却或换号。
3. **Access Token 换取**：
   * 每次使用账号时用 Refresh Token 换取 Access Token；同一请求的上游重试复用该令牌。不使用进程内 Token 缓存或并发单飞锁。永久失效的 Refresh Token 会将账号标记为失效，供后续请求选择账号时跳过。
4. **Google 项目编号**：
   * 以 Antigravity Cloud Code PA 的 `loadCodeAssist` 返回的 `cloudaicompanionProject` 为准；未返回时根据 `allowedTiers` 调用 `onboardUser` 获取托管项目。组织账号可显式提供项目 ID。
   * 旧数据中的 `aicode-consumers` 不再被当作自动默认值；每次换票后重新核对 Google 返回的编号。无法确定编号时报错，不构造虚假的项目编号。
   * 已保存的推理能力作用域包含项目 ID。如果账号的真实编号与旧作用域不同，需重新探测相应模型的 effort 档位。

Google OAuth 客户端、令牌、跨设备使用和当前网关鉴权边界的实现细节见[Google 专线认证与项目编号](./Google专线认证与项目编号.md)。

### 8.2 账号管理方式
提供 **CLI 交互指令** 与 **Ingress REST API** 双重管理能力：

#### 1. CLI 命令行运维
* **查看账号状态**：`npm run account:list`
* **交互式浏览器 OAuth 登录**：`npm run account:login`（临时启动本地回调端口接收 Google 授权，再从 Cloud Code PA 获取项目 ID）
* **手动导入 Refresh Token**：`npm run account:add -- <refresh_token> [label] [projectId]`
* **删除指定账号**：`npm run account:remove -- <email_or_id>`

#### 2. REST API 动态管控（需携带网关 Bearer Token）
* `GET /v1/admin/google/accounts`：查询账号池列表与有效性；
* `POST /v1/admin/google/accounts`：新增凭据（请求体：`{ "refreshToken": "...", "label": "..." }`）；
* `DELETE /v1/admin/google/accounts/:id`：移除账号；
* `PATCH /v1/admin/google/accounts/:id`：启用/禁用指定账号；
