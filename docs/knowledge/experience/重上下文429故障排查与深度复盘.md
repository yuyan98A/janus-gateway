# Claude Code 接入 Google Antigravity 重上下文 429 故障排查与深度复盘

> [!NOTE] **文档定位说明**  
> 本文档为新网关项目启动前的**上游 Google 云端风控（Identity Scrubbing 与 WAF 审查）前置测试与排查经验资产**，供开发 Google 驱动脱敏模块时参考，**非新项目的主体架构**。  
> 正在进行的统一多云网关核心设计请参阅主文档：👉 [**全能多云反向代理网关架构设计方案**](../多云反向代理网关架构设计方案.md)。

本文档记录了在使用重型 Agent 上下文（15 个 Skill、6 个 Subagent、30 个 Tool、`CLAUDE.md`，单次请求 ~144 KB / 37,000+ tokens）接入 Google Antigravity / Cloud Code 时，出现的 `400/429 RESOURCE_EXHAUSTED` 故障从现象、假设、推导、实测二分验证到最终根因定位的完整排查过程与方法论沉淀。

---

## 1. 故障现象与背景

### 1.1 初始环境与上下文
* **开发环境**：Windows 11, PowerShell, Node.js v24
* **客户端**：Claude Code CLI (v2.1.284.12a)，配置通过 CC Switch 注入
* **中间网关**：`antigravity-claude-proxy` (v1.110.0) 监听本地 8080 端口
* **上游资源**：Google One AI Premium（内置 `aicode-consumers` 项目）
* **上下文特征**：用户配置了重度工程环境，包含 15 个 Skill、6 个 Subagent、30 个 Tool 及复杂系统规则，初次对话上下文高达 ~144 KB / 37,000+ tokens。

### 1.2 故障现象
在终端中启动 Claude Code CLI，输入首句测试文本：
```text
> 你好
```
等待十几秒后，终端立即弹出致命红字报错退出：
```text
● API Error: 400 RESOURCE_EXHAUSTED: You have exhausted your capacity on gemini-3. Quota will reset after 30m0s.
```
切换到 Claude 模型（如 `claude-sonnet-4-6`）同样抛出：
```text
● API Error: 400 RESOURCE_EXHAUSTED: You have exhausted your capacity on claude-sonnet-4-6. Quota will reset after 30m0s.
```
且在此之后，哪怕发送最简单的单个词汇，代理网关也在 0 毫秒内瞬间报错拒绝。

## 2. 深度排查与破案路径

### 步骤 1：排查服务存活性与账号真实配额（排除假象）
1. **本地极简探针测试**：
   使用独立脚本直接向 `http://localhost:8080/v1/messages` 发送仅包含 `"Say hello"` 的请求：
   * **结果**：HTTP 200 OK，耗时 2.1 秒。
   * **推论**：代理服务是健康的，Google 账号能够正常出字。
2. **查询 Google 后端真实配额**：
   通过代理的 `/account-limits` 接口提取 Google 后端返回的真实剩余额度：
   * `claude-sonnet-4-6` / `claude-opus-4-6-thinking`：**剩余配额 86.5%**
   * `gemini-3.8-flash-high` / `gemini-2.5-pro`：**剩余配额 60.4%**
   * **推论**：**用户的 Google 配额从来没有耗尽！**“配额耗尽”是一个假象。

### 步骤 2：捕获全量真实请求现场
在网关入站中间件处挂载临时 Dump 逻辑，捕获 Claude Code 启动时的真实报文：
* 报文体积：143,457 字节（~144 KB）
* 工具数量：30 个 Tools
* 系统提示：包含多段 System Blocks，首段为 `x-anthropic-billing-header: cc_version=...`，第二段为 `You are a Claude agent, built on Anthropic's Claude Agent SDK.`

### 步骤 3：压力与容量极限测试（排除体积假设）
为了验证是否是 Google 或代理层限制了“大报文”：
* **构造测试**：编写脚本生成 1,000 ~ 30,000 单词（约 45,000 tokens / 180 KB）的纯英文文档作为上下文。
* **执行结果**：发往 Google 后，**在 2.8 秒内成功返回 HTTP 200 OK**！
* **推论**：**绝对不是上下文体积（Token 数量）超标的问题**。Google 完全可以承载 45,000 tokens 的大请求。

### 步骤 4：单变量拆解与二分排查（锁定元凶）
编写独立的脱机探针脚本，绕过 Claude Code CLI 直接将捕获到的报文按维度拆解发送给 Google：

| 实验组 | 发送内容结构 | 测试结果 | 关键推论 |
| :--- | :--- | :--- | :--- |
| **Candidate A** | Claude System 提示词 + 简短 User 问题 | **Status 429 RESOURCE_EXHAUSTED** | 证实问题 100% 潜伏在 System Prompt 中！ |
| **Candidate B** | Claude Messages（含 7 个上下文提醒）+ 简短 System | **Status 200 OK** | 证实 Messages 内部的 Reminder 完全合法。 |
| **Candidate C** | Claude System 提示词（中和掉 `Anthropic`/`Claude`） | **Status 200 OK** | 证实只要脱敏，整段 System Prompt 完全被放行！ |
| **Candidate D** | 等长（15,000 字符）假 System 规则 | **Status 200 OK** | 进一步证实不是 System 的长度限制。 |

### 步骤 5：单字命中定位
对 System Prompt 实施更精细的单变量替换：
1. **仅替换 `Anthropic`** $\rightarrow$ **Status 200 OK**（即时秒回）！
2. **仅替换 `Claude`，保留 `Anthropic`** $\rightarrow$ **Status 429 RESOURCE_EXHAUSTED**！
3. **移除 Billing Header，保留剩余文本** $\rightarrow$ **Status 429 RESOURCE_EXHAUSTED**（因为文本里还有 `built on Anthropic's Claude Agent SDK`）。

**真凶彻底锁定**：
Google Cloud Code PA 内部针对第三方法人/竞争对手 Agent 设置了黑名单过滤机制：**只要在 `systemInstruction` 中检测到关键词 `"Anthropic"`，Google 就故意返回一个虚假的 `429 RESOURCE_EXHAUSTED`（伪装成配额耗尽）以此阻断竞品 SDK。**

## 3. 本次遇到的所有重要问题

### 问题 1：首句对话即报 400 RESOURCE_EXHAUSTED

* **现象**：Claude Code 敲入 `> 你好`，10 多秒后报 `API Error: 400 RESOURCE_EXHAUSTED: You have exhausted your capacity on gemini-3...`。
* **最初判断**：以为 Google 账号免费额度用完，或者 37k 上下文超出了代理单次请求限制。
* **真正原因**：
  1. Claude Code 强制在 System Prompt 开头注入 Anthropic 计费头与身份说明。
  2. Google Cloud Code PA 后端设置了防爬机制：**只要 `systemInstruction` 出现 `"Anthropic"`，上游就故意抛出一个虚假的 `429 RESOURCE_EXHAUSTED`**。
  3. 网关轻信了此报错，直接将账号持久化标记为“限流 30 分钟”，后续请求在网关本地直接被抛 400 阻断。
* **解决方案**：
  在 `src/cloudcode/request-builder.js` 中加入脱敏规则：
  ```javascript
  const DEFAULT_IDENTITY_SCRUB = [
      ['Nous Research', 'the assistant team'],
      ['Hermes Agent', 'the assistant'],
      ['Hermes', 'the assistant'],
      ['Anthropic', 'AssistantCorp'],
      ['anthropic', 'assistantcorp'],
      ['ANTHROPIC', 'ASSISTANTCORP']
  ];

  function scrubClientIdentity(text) {
      if (typeof text !== 'string') return text;
      let out = text;
      for (const [term, replacement] of IDENTITY_SCRUB_RULES) {
          out = out.split(term).join(replacement);
      }
      out = out.replace(/Anthropic/gi, 'AssistantCorp');
      return out;
  }
  ```
* **为什么有效**：避开上游 WAF 针对竞品 SDK 的过滤规则。

---

### 问题 2：网关本地 Rate Limit 状态级联死锁

* **现象**：一旦触发过一次 429，哪怕后续用户发最简单的请求，也在 0 毫秒内瞬间报错，上游无网络请求。
* **最初判断**：以为 Google 后端封禁了 IP 或 Session。
* **真正原因**：网关在收到 429 后，将 `isRateLimited: true` 写入磁盘文件 `~/.config/antigravity-proxy/accounts.json`。在 30 分钟倒计时结束前，本地中间件直接拦截抛出 400。
* **解决方案**：重置 `accounts.json` 中对应模型的限流标记，将 `isRateLimited` 恢复为 `false`。
* **以后如何更快发现**：如果报错耗时 $<50\text{ms}$，直接断定为**本地中间件短路拦截**，优先查阅本地持久化配置。

---

### 问题 3：生产端点与日常端点分化（Prod vs Daily）

* **现象**：直连探针测试中，`cloudcode-pa.googleapis.com` 连 `hi` 都返回 429，而 `daily-cloudcode-pa.googleapis.com` 全部秒通。
* **最初判断**：以为账号全局被禁。
* **真正原因**：Google 内部端点策略差异，个人订阅 Token 在生产集群受限严苛，而日常集群与 Antigravity IDE 官方客户端完全一致，配额分配宽容。
* **解决方案**：网关路由写死优先请求 `daily-cloudcode-pa.googleapis.com`。
* **以后如何更快发现**：逆向或自建中继时，提取官方 IDE 客户端二进制通信日志，确认官方默认 Host。

## 4. 失败方案与弯路复盘

### 弯路 1：怀疑上下文太重，试图删减 Skills / Tools
* **当时为什么会想到**：报错明确写着 `RESOURCE_EXHAUSTED`，且短对话能通，长对话必崩，极度符合“爆 Token”的直觉。
* **为什么失败**：因为 45k tokens 的纯文本完全可以通过。上下文大只是载体，大载体里夹带的敏感词才是因果。如果盲目让用户删 Skill，不仅无法解决问题，还破坏了开发环境。
* **认知误区**：**“相关性不等于因果性”**。
* **如何避免**：第一时间做**“纯净等体积 Dummy Payload 压力测试”**，如果纯文本能通，立即彻底排除体积原因。

### 弯路 2：怀疑 30 个 Tool 的 Schema 格式有兼容 Bug
* **当时为什么会想到**：Gemini Function Calling 对 JSON Schema 要求苛刻，怀疑是某个 Skill 的 Tool 结构引发上游报错。
* **为什么失败**：把 30 个 Tool 全删掉只留 System Prompt，依然报 429。
* **认知误区**：未做二分排查就陷入琐碎的细节求证。
* **如何避免**：**自顶向下二分剥离**。优先在最外层把整个 `tools` 字段置空测试，再考虑是否需要深入内部。

### 弯路 3：轻信社区“Google Cloud Code 严苛限流不可用”的讨论
* **当时为什么会想到**：网络论坛上大量帖子称 Google 免费配额很容易崩溃。
* **认知误区**：**从众心理与信息茧房**。很多发帖者自己也没能定位到底层竞品词过滤的真相。
* **如何避免**：以一手抓包数据和代码执行证据为唯一准绳。

## 5. 技术知识提炼

### 1. 现代云厂商的“竞品身份指纹拦截”（Opaque 429）
* **原理**：云厂商设置的内容审查规则，专门识别竞品 Agent 标识符（如 Anthropic SDK、AutoGPT 等）。厂商为了避免直接返回 403 引发公关纠纷，狡猾地将其伪装成 **`429 RESOURCE_EXHAUSTED`**。
* **应对**：在网关层建立中和清洗管道（Sanitizer），将厂商标识映射为中立占位符（如 `AssistantCorp`）。

### 2. SSE 首包缓冲策略（First-Chunk Buffering）
* **原理**：若在收到上游第一个 Chunk 之前就提前执行了 `res.writeHead(200)`，一旦上游首包报错（如 429/500），网关无法再改写 HTTP 状态码，导致下游 CLI 报协议解析崩溃。
* **实践**：必须在内存中成功拉取到第一条有效业务 Chunk 之后，才执行 `res.flushHeaders()` 输出 200 OK。

### 3. Agent 客户端上下文的全载荷特征
* **原理**：用户键入一句“你好”，实际发送的上下文包含了系统内置预设、CLI 约束、项目文件树、所有 Skills 以及所有 Tools 的 Schema 定义。
* **认知**：在大模型 Agent 开发中，**“第一句话就是全载荷”**。

## 6. 可复用问题排查方法论

面对黑盒 API 复杂报错的标准推演法：

```text
[现象] (API 报 400/429 RESOURCE_EXHAUSTED)
  │
  ├─ 1. 确认真实边界: 查验网关账号真实余量 (否定"额度耗尽"猜想)
  │
  ├─ 2. 捕获完整现场: 落盘客户端原始 HTTP Headers & Body
  │
  ├─ 3. 构造脱机探针: 编写独立 test_probe.mjs 绕过 CLI 干扰
  │
  ├─ 4. 二分维度排查:
  │      ├── 纯净体积测试 (排除 Token/大小限制)
  │      ├── 结构组件剔除 (排除 Tools/Messages/System)
  │      └── 单变量词汇替换 (精确定位触发敏感字)
  │
  └─ 5. 最小切口修复: 在网关针对性脱敏 -> 重放验证 -> 客户端回归
```

* **黄金法则**：只要一个黑盒 Bug 排查超过 15 分钟，**立即停止盲目试错，花 5 分钟写一个脱机探针脚本**。

## 7. 工程设计上的经验与技术债警示

1. **状态机自锁陷阱（严重技术债）**：
   * 网关把上游的 429 粗暴判定为“账户限流”并死锁磁盘，导致单次语义拦截升级为全账号瘫痪。
   * **优化建议**：细分 `QUOTA_EXHAUSTED`（真耗尽）与 `CONTENT_BLOCKED`（语义拦截），语义拦截绝不能锁定全局账号。
2. **无侵入拦截设计（优秀实践）**：
   * 在网关内部脱敏，不需要篡改 Claude Code 客户端打包源码，保障了客户端未来随官方平滑升级。

## 10. 工程师个人经验库

> **经验 1：不要轻信云厂商 4xx/429 报错的字面描述**  
> *为什么*：现代云平台为了防逆向和反爬，经常故意把“策略审查拦截”伪装成“资源耗尽（429 Too Many Requests）”。  
> *今天证明*：Google 返回“配额已耗尽，请 30m 后重试”，而账号真实配额高达 86.5%，真实原因仅仅是 System 出现了 `"Anthropic"` 这个词。  
> *何时想起*：以后凡是遇到控制台显示有额度、极简调用能通、但复杂业务必报 429/400 时，第一反应必须是“黑名单/内容审查拦截”。

> **经验 2：警惕“容量陷阱”，相关性不等于因果性**  
> *为什么*：重载系统出问题时，人本能地会归咎于“太大太重了”，从而浪费大量时间去做无意义的配置删减。  
> *今天证明*：Claude Code 携带 144 KB 失败，但我们塞入 180 KB 纯文本秒通。证明“体积大”只是假象，体积里夹带的“敏感特征”才是根因。  
> *何时想起*：排查容量或超限 Bug 前，务必先用无意义的“纯净基准载荷（Dummy Payload）”探针彻底排除体积因素。

> **经验 3：自锁状态机会把一个瞬时拦截演变成全局灾难**  
> *为什么*：防御性编程如果缺乏自愈和细分机制，会把单次失败当成全局状态持久化，从而导致系统丧失自愈能力。  
> *今天证明*：网关把一次竞品拦截当成全账号封禁，写入磁盘锁定 30 分钟，导致代码哪怕改对了也会在本地被秒拒。  
> *何时想起*：在设计断路器（Circuit Breaker）、熔断器和本地限流表时，必须具备轻量探测与快速自愈逻辑，切忌轻易落盘死锁。

> **经验 4：独立脱机探针的投资回报率是最高的**  
> *为什么*：通过复杂的终端应用调试协议，每次都有大量无关输入、动画延迟和封装遮蔽。  
> *今天证明*：写一个 30 行的 `test_probe.mjs`，5 分钟内完成了 4 组精确单变量测试，瞬间定位真因。  
> *何时想起*：只要一个问题排查超过 15 分钟，立即停下来写独立复现脚本。

> **经验 5：协议网关的最高境界是对上下游的“双向透明欺骗”**  
> *为什么*：下游客户端有其固化的生态指纹，上游云平台有其严格的防线规则。  
> *今天证明*：最好的解法不是逼用户删减 Skills 妥协，也不是反编译破解客户端，而是在中间网关层做“移花接木”：对下满足 Anthropic SSE 规范，对上抹平一切竞品痕迹。  
> *何时想起*：在做任何 API 聚合、中继代理和跨生态融合架构设计时。
